Market context: what “RAG MVP” usually means on talent marketplaces

Clients comparing proposals see the same shapes repeatedly. None of these are “wrong,” but they solve different problems than a serious internal library tool. This catalog is written so your scope reads as operator-grade, not a weekend tutorial fork.

Common archetypeWhat it typically deliversWhere it often stops
Chat-with-PDF / single-notebook RAG Upload one PDF, ask questions in a chain; OpenAI + Pinecone or FAISS; citations as an afterthought. No durable API contract, no readiness checks, weak bulk ingest, one generic prompt, little cross-document behavior.
Streamlit-only UI Fast POC for a solo analyst; good for iteration. Harder handoff for product/engineering teams; limited layout for ops workflows and dashboards.
Cloud-only stack (managed vectors + hosted LLM) Lowest friction first demo. Data residency and unit economics may disqualify regulated or IP-heavy libraries unless redesigned.
Agent demos (many tools, thin retrieval) Impressive transcripts on cherry-picked threads. Opaque failure modes; retrieval quality and citation discipline often underspecified in acceptance criteria.
Vector search SKU Semantic search endpoint only. No grounded generation contract, no query modes, no operator story for ingest and review.

Many public “ChatPDF” repos share the same shallow shape: single chain, hosted keys assumed, weak acceptance criteria. Procurement and internal platform teams ask for health semantics, API contracts, and repeatable ingest — the gap this catalog closes.

What makes this catalog stand out for buyers

  • Written acceptance criteria per milestone (ingest success, non-empty citations, readiness check) so escrow maps to verifiable deliverables.
  • Dual health model (liveness vs readiness) aligned with how platform teams deploy behind proxies.
  • Retrieval behavior spelled in (top-k, optional section filter, rerank / diversity) so one paper cannot dominate context—a frequent failure in generic RAG demos.
  • Multiple grounded query modes (not only Q&A): comparison, methodology, structured dataset hints, reproducibility-style checklist—signals research-adjacent use, not a single chat box.
  • Deployment + runbook + bounded support so handoff is contractual, not an ad-hoc repo drop.

What the client receives

  • Ingestion pipeline for agreed formats (typically PDF, DOCX, TXT) with size limits, validation, and clear error responses.
  • Chunking + embeddings + vector store with metadata for citations (document id, section hint, page or chunk index).
  • Retrieval layer with top-k search, optional section filter, and basic rerank / diversity so one document does not dominate answers.
  • Generation with at least two query modes (e.g. general Q&A + compare or methodology) and source cards returned with each answer.
  • REST API (OpenAPI spec), health and readiness endpoints suitable for a reverse proxy or container orchestrator.
  • Operator UI to upload documents, run queries, and inspect sources (framework can match client stack; reference uses Next.js + FastAPI).
  • Deployment to one agreed environment (e.g. single VM + Docker Compose, or one managed container service).
  • Handoff: README runbook, .env.example, and a 30-minute recorded walkthrough or live session (client choice).
  • Support: 14 calendar days of bugfix support for defects reproducible on the agreed deployment (not new features).

Out of scope (Phase 2 unless contracted)

  • Per-document or per-tenant access control beyond a single shared library.
  • Formal legal/compliance sign-off, penetration testing, or SOC2 evidence packs.
  • Training or fine-tuning custom LLMs on client proprietary data.
  • OCR for low-quality scanned PDFs beyond a basic pass (can be scoped separately).
  • SLA with 24/7 on-call or sub-minute incident response.

Client responsibilities

  • Provide sample documents (or permission to use public corpus) and a single technical point of contact.
  • Provide or approve LLM access (API keys, VPC endpoints, or approval to run Ollama on agreed hardware).
  • Provide deployment target credentials or a sandbox subscription for the agreed cloud.
  • Review milestone deliverables within 5 business days of submission.
